# 10 技術構成の概略

ステータス:**確定 v1.0(2026-11-06)**
前提:`07` v1.0(MVP は ① のみ、約60時間)、`08`、`09` v1.0(15個の表)

---

## 1. 決めること(全体像)

プロダクトは、ざっくり次の4つの部品でできている。

```
[スマホ・PC の画面] ── 写真を上げる、確認する、結果を見る
        │
[アプリ本体] ── 計算(濃度・上限との比)、データの出し入れ
        │                     │
[データベース]           [Claude API]
 処方・精油・IFRA・記録    写真の読み取り
```

| # | 決めること | 選択肢の数 |
|---|---|---|
| T1 | 画面とアプリ本体を、何で作るか | 3案 |
| T2 | データベースを、何にするか | 3案 |
| T3 | 指標をどこで見るか(ダッシュボード) | 2案 |
| T4 | 不変 ID の形 | 2案 |
| T5 | AI のモデル | 実装の中で Evals で比べて決める |

---

## 2. T1:画面とアプリ本体

| 案 | ひとことで言うと | 良いところ | 気になるところ |
|---|---|---|---|
| **(a) 一般的な Web アプリ**(例:Next.js) | 普通の Web サービスと同じ作り方 | スマホでもきれいに使える。見た目や操作を細かく作れる。ポートフォリオとして「ちゃんとしたサービス」に見える。Claude Code が得意な作り方 | 部品が多く、最初の準備に時間がかかる(数時間) |
| **(b) データ分析向けの簡単な画面**(例:Streamlit) | Python で、表やボタンのある画面をすばやく作る道具 | 作るのが一番速い。表やグラフを出すのが簡単 | 見た目の自由度が低い。スマホでの写真の上げ下ろしや細かい操作は、(a)より使いにくい |
| **(c) スプレッドシート+スクリプト**(Google スプレッドシート+Apps Script) | 今の道具の延長 | なじみがある。画面をほぼ作らなくてよい | 写真の読み取りや確認画面のような「流れ」を作りにくい。SQL を使う見せ場がなくなる(ポートフォリオの条件を満たしにくい) |

- 【推測】提案:**(a)**。理由:毎日スマホで写真を上げて確認する流れ(09:定着)には、スマホで使いやすい画面が大事。60時間のうち数時間を準備に使っても見合う。
- 時間をとにかく節約したい場合は (b)。
- **決定(2026-11-06):(a) 一般的な Web アプリ**(ひろみ)。MVP の後に (g)(Claude のアプリを入口にする)を追加することを検討する。

### 別案(2026-11-06、ひろみの依頼で追加)

| 案 | ひとことで言うと | 良いところ | 気になるところ |
|---|---|---|---|
| **(d) ノーコードのアプリ作成ツール**(例:Glide、AppSheet、Softr、Bubble) | 画面を組み立てるだけでアプリを作るサービス | スマホ向けの画面がすぐできる。コードをほぼ書かない | 写真を Claude API に送る部分は、つなぎ込みの工夫が要る。ツールの料金・制限に縛られる。SQL を見せにくい場合がある |
| **(e) 社内ツール作成サービス**(例:Retool) | データベースの上に、管理画面をすばやく作るサービス | 表・フォーム・ボタンの画面が速く作れる。SQL を直接書ける | スマホでの写真の扱いは弱め。料金体系の確認が必要 |
| **(f) LINE のボット** | LINE に写真を送ると、結果が返ってくる | スマホで一番手軽。いつも使うアプリの中で完結する | 表の確認・修正のような細かい操作は、チャットではやりにくい。結局、確認用の画面が別に要る |
| **(g) 画面を作らず、Claude のアプリを画面にする**(MCP を使う) | Claude のアプリに写真を送ると、Claude が MCP 経由でデータベースに保存し、確認結果を返す | 画面をほぼ作らなくてよい。**MCP を本格的に経験できる**(学びの目的に合う)。話しかけるように使える | Claude のアプリ側のデータの扱いは、API と規約が異なる(08 の確認とは別に要確認)。確認画面のような決まった流れは作りにくい。「アプリに Claude API を組み込む」形ではなくなるので、ポートフォリオの条件の見せ方が変わる |

- 【推測】(g) は、②で予定している MCP(Next)を先取りする形でもある。MVP の中心にするより、**MVP の後に「(a) のアプリ+ (g) の入口」を足す** のが、リスクが小さい。

## 3. T2:データベース

| 案 | ひとことで言うと | 良いところ | 気になるところ |
|---|---|---|---|
| **(a) Supabase**(PostgreSQL) | ネット上で使えるデータベース。写真の保存場所とログインの仕組みもついている | 本格的な SQL がそのまま使える(ポートフォリオの条件)。写真の保存・ログインを別に用意しなくてよい。管理画面から SQL を直接書いて集計できる | 外部のサービスに頼る。無料枠の範囲を確かめる必要がある(要確認) |
| **(b) SQLite** | ファイル1つのデータベース | とても手軽。費用がかからない | ネットに公開して、スマホから使うのには向かない |
| **(c) BigQuery** | ひろみが使い慣れた分析用データベース | ひろみが SQL に慣れている | 1件ずつの登録・更新(アプリの普段の動き)には向かない。分析専用 |

- 【推測】提案:**(a) Supabase**。アプリの普段の動きと、SQL での集計の両方に使える。

### 別案(2026-11-06 追加)

| 案 | ひとことで言うと | 良いところ | 気になるところ |
|---|---|---|---|
| **(d) Neon などの PostgreSQL 専用サービス** | Supabase からデータベース部分だけを取り出したようなもの | 本格的な SQL。シンプル | 写真の保存・ログインを別に用意する必要がある |
| **(e) Google Cloud SQL**(PostgreSQL) | Google Cloud のデータベース | ひろみが慣れた Google Cloud の中でそろう。Looker Studio との相性がよいと思われる【要確認】 | 設定・管理の手間と費用が、Supabase より大きい傾向【推測】 |
| **(f) Firebase(Firestore)** | Google のアプリ向けデータベース | アプリとの連携が簡単 | SQL ではない(ポートフォリオの条件を満たしにくい)。表どうしをつなぐ集計(09)に向かない |

- 【推測】提案は (a) のまま。写真の保存とログインまで1つでそろい、60時間の中での準備が一番少ないため。
- **決定(2026-11-06):(a) Supabase**(ひろみ。「使ったことないけど、提案どおりにしてみる」)。

## 4. T3:指標を見る場所

| 案 | 良いところ | 気になるところ |
|---|---|---|
| **(a) アプリの中に、指標のページを1つ作る** | ひとつの場所で済む | 作る手間(2〜3時間)が 07 の見積もりに追加で必要 |
| **(b) Looker Studio などの BI ツールを、データベースにつなぐ** | グラフを自由に作れる。ひろみの分析の経験が活きる。SQL を書いて見せられる | つなぐ設定が必要。ツールが別になる |

- 【推測】提案:**(b)**。07 の見積もり(R17:記録と SQL での集計)に収まりやすく、ひろみが SQL を書く場面にもなる(エンジニアと対等に話す練習)。
- **決定(2026-11-06):(b) Looker Studio**(ひろみ)。
- 注:Looker Studio が Supabase(PostgreSQL)につなげられるかは、実装の前に確認する【要確認】。

## 5. T4:不変 ID の形

ノートに手書きし、写真から読み取るので、**書きやすく、読み間違えにくい** ことが大事。

| 案 | 例 | 良いところ | 気になるところ |
|---|---|---|---|
| **(a) 短い連番** | `P042` | 書きやすい。順番が分かる | 桁が増えると書く量が増える(当面は3桁で足りる見込み:月30前後 × 数年で数百件) |
| **(b) ランダムな文字** | `K7QX` | 推測されにくい | 書き写しにくい。O と 0、I と 1 などの読み間違いが起きやすい |

- 【推測】提案:**(a) 短い連番**。先頭の文字は、読み間違えにくい1文字に固定する(例:P)。
- **決定(2026-11-06):P+5桁の連番(例:`P00042`)**。理由:練習の香りも毎日記録するので、3桁(999件)ではすぐ埋まるおそれがある(ひろみ)。

## 6. T5:AI のモデル

- 写真の読み取りの精度と、1回あたりの費用・時間で選ぶ(09:K8・K9)。
- 【推測】進め方:実装の中で、**正解データ(05 の3ページ+α)を使って、2つ程度のモデルを比べる(Evals)**。精度が同じなら、安くて速い方を選ぶ。
- 具体的なモデル名と料金は、実装を始めるときに最新の情報で確認する(この文書では決めない)。

## 7. そのほかの前提

- **写真の形式**:iPhone の HEIC を受け付けて、アプリの中で変換する(07 R1)。
- **ログイン**:利用者はひろみ1人。ログインはつける(処方は企業秘密のため)。
- **IFRA の版**:第51次改正のデータを取り込み、版の情報を持つ。第52次改正(2027年1月予定)が出たら追加で取り込む(09)。
- **費用**:データベース・公開の無料枠と、Claude API の利用料がかかる。金額は実装を始めるときに最新の料金で見積もり、実装の中で K9 として実測する。【要確認】
