# 質問と迷いの記録(復習用)

- ひろみが作業中に質問したこと・迷ったことを、あとで復習できるように残す。
- 「ひろみの質問」はひろみの言葉のまま。「答えの要点」は Claude の説明を短くまとめたもの。
- 新しいものを下に足す。学びのログ(`learning-log.md`)は節目のふり返り、このファイルは日々の疑問の記録。
- 最後に用語集を置く。

## ツールの地図(どのツールが何をしているか)

```
[ひろみのスマホ・PC のブラウザ]
        │  https://〜.netlify.app を開く
        ▼
[Netlify] … アプリを置いて、ネットに公開している場所
        │  中で動いているのが ↓
[Next.js のアプリ](リポジトリの web/ フォルダ)… 画面と、裏の処理
        │                         │
        ▼                         ▼
[Supabase]                   [Claude API](写真の読み取りを作るときから使う)
 ・ログインの仕組み
 ・データベース(処方・精油・IFRA)
 ・写真の保存場所

[GitHub] … コードと docs/ の置き場所。変更の歴史(コミット)と、確認(PR)
   └ PR を作る・更新すると、Netlify が自動で「確認用の版」を組み立てる
   └ main に取り込む(マージ)と、Netlify が本番を組み立て直す

[Claude Code(この会話)] … コードと docs/ を書いて、GitHub に送る
```

| ツール | 一言で | ひろみが触る場面 |
|---|---|---|
| GitHub | コードと文書の置き場所・変更の確認 | PR を見る、マージする |
| Netlify | アプリをネットに公開する | 環境変数を入れる、組み立てをやり直す |
| Supabase | ログイン・データベース・写真の保存 | ユーザーを作る、SQL を実行する、データを見る |
| Next.js | アプリの作り方(枠組み) | 直接は触らない |
| Claude API | アプリから AI を呼び出す窓口 | キーを用意する(済み) |
| Looker Studio | 指標のグラフ | 計測(R17)のとき |

## 2026-11-06 実装フェーズの準備(土台 R18)

### Q1. Supabase の Region
- **ひろみの質問**:「regionはap-southeast-1なのかな?」
- **答えの要点**:
  - `ap-southeast-1` はシンガポール。東京は `ap-northeast-1`。
  - Region は作ったあとに変えられない。中身が空のうちなら、消して作り直すのが一番楽。
  - 遠いと画面の反応が少し遅くなる(シンガポールだと東京より 0.07秒ほど)。利用者が1人なら実害は小さい。
- **結果**:東京で作り直した。

### Q2. 「Asia-Pacific」を選べばよいか
- **ひろみの質問**:「region、asia-pacificでいい?」
- **答えの要点**:
  - 「Asia-Pacific」のような大きな地域を選ぶと、その中のどこに置くかは Supabase が決める(最初にシンガポールになったのはたぶんこれ)。
  - 個別の地域を選べる表示に切り替えて「Tokyo」を選ぶ。

### Q3. さくらサーバを使えないか
- **ひろみの質問**:「わたしさくらサーバを持ってるんだけどそこは変?」
- **答えの要点**:
  - 変ではない(持っているものを使えば費用が増えない)。
  - ただ、Next.js のアプリは「サーバの上で常に動いているプログラム」が要る。共用のレンタルサーバでは、それを置き続けられないことが多い。
  - VPS なら動かせるが、サーバの手入れ(更新・セキュリティ)を自分で続ける必要がある。
- **結果**:Netlify(無料プラン)に置く。

### Q4. ドメインはどうするか
- **ひろみの言葉**:「ドメインは持ってる!まぁあとあと移管するとかでいいか。」
- **答えの要点**:
  - 【推測】ドメインの「移管」(管理する会社を変えること)は要らない。持っているドメインの設定で、`tool.polearoma.com` のような住所を Netlify に向けるだけでよい。
  - 後でやる。

### Q5. 「PR を見張る」とは
- **ひろみの質問**:「これどういうこと?具体的におしえてほしいな」
- **答えの要点**:
  - PR で何か起きたら(Netlify の組み立ての失敗、コメントなど)、GitHub から Claude に知らせが届き、Claude が見て対応する。
  - 見張っていないと、ひろみが気づいて伝えるまで、失敗がそのままになる。
  - Claude が PR を `main` に取り込む(マージ)ことはしない。Netlify の管理画面やスマホでの結果は、Claude からは見えない。

### Q6. Netlify の設定画面が見つからない
- **ひろみの言葉**:「Project configurationがみつからないなー」→「あ、githubの該当リポジトリとの接続ができてなかったみたい」
- **答えの要点**:
  - サービスの画面の名前はよく変わる(Claude の案内が古いこともある)。見つからないときは、並んでいる項目の名前を伝えると早い。
  - 実際の原因は、Netlify とリポジトリがまだつながっていなかったこと。

### Q7. Netlify の Build settings に何を書くか
- **ひろみの質問**:「Build settingsって何を書けばいいの?」
- **答えの要点**:
  - Branch to deploy:`main`(本番として公開するブランチ)
  - Base directory:`web`(アプリ本体のフォルダ)
  - Build command:`npm run build`(アプリを組み立てる命令)
  - Publish directory:`web/.next`(組み立てた結果の置き場所。自動で入ればそのまま)
  - 実際は、リポジトリの `netlify.toml` に書いた設定が優先される。

### Q8. Supabase の URL と publishable key は「秘密の値」か
- **ひろみの質問**:「ちなみにこれって「秘密の値」に該当する??」
- **答えの要点**:
  - どちらも厳密には秘密ではない。URL は「住所」。publishable key は、ブラウザに渡しても大丈夫なように作られたキー。
  - 安全なのは、データベースの表ごとに「誰が読める・書けるか」の決まり(RLS)を付けている場合だけ。処方の表を作るときは必ず付ける。
  - 本当に秘密なのは、Claude API のキーと Supabase の Secret key(知られると、お金を使われる/データベースに何でもできる)。
  - それでもチャットやリポジトリには書かない(毎回「書いていいキーか」と迷わないため)。

### Q9. Netlify が「秘密の値にしろ」と何度も勧めてくる
- **ひろみの質問**:「って注釈出てるけど大丈夫なのかな」「ってもう一回言われたよ〜〜」「これってsupabaseのpole-aroma-work-managementのproject URLなんだよね?」
- **答えの要点**:
  - 【推測】Netlify は値の中身ではなく、名前(URL・KEY など)だけを見て一律に注意を出している。
  - そう、Supabase のプロジェクトの Project URL(`https://〜.supabase.co`)。
  - チェックしてもしなくても、安全面の差はほとんどない。チェックすると、値があとで見られなくなるだけ。

### Q10. 本番の組み立てが失敗した
- **ひろみの言葉**:「Deploy failed for pole-aroma-work-management って出たなぁ」
- **答えの要点**:
  - 想定どおり。`main` にまだアプリ本体(`web/`)がないため。PR を取り込めば通るはず。
  - PR 用の確認版(Deploy Preview)は成功した。

### Q11. 確認はスマホでないとだめか
- **ひろみの質問**:「これはスマホで見ないとだめ?PCは微妙?」
- **答えの要点**:
  - ログインの確認なら PC で十分。
  - スマホで確かめる意味が大きくなるのは、写真を上げる画面(R1)を作ってから(HEIC、カメラからの撮影)。

### Q12. PR の「Draft pull requests cannot be merged」
- **ひろみの質問**:「まだ作ってるのか、なんか失敗してるかなぁ?」
- **答えの要点**:
  - 失敗ではない。Claude が PR を「下書き(Draft)」で作ったため。下書きの間はマージのボタンが押せない(間違えて取り込まないため)。
  - 確認が終わったら下書きを解除する。

### Q13. 確認用の URL が「Page not found」になる
- **ひろみの言葉**:「page not foundになっちゃった」「Netlifyの画面っぽい見た目だなぁ」
- **何が起きていたか**:
  - 【事実】Next.js を Netlify で動かすための仕組み(`@netlify/plugin-nextjs`)が動いておらず、組み立てた結果がただのファイルとして置かれていた。どの URL も見つからない状態。
  - 最初は「公開フォルダの指定ミス」を疑って直したが、原因ではなかった。Claude の作業環境で Netlify の組み立てを再現して、本当の原因が分かった。
  - 設定ファイル(`netlify.toml`)に、この仕組みを使うことをはっきり書いて直った。
- **学び**:
  - 「組み立て成功(Deploy Preview ready)」でも、ページが開けるとは限らない。最後は実際に開いて確かめる。
  - 画面の見た目(Netlify の 404 か、アプリの 404 か)で、どこで止まっているかの見当がつく。

### Q14. Netlify の Bot のコメントが動いていない?
- **ひろみの言葉**:「netlify Botが#2に来てないみたい?」「botがきてるけど、それ以降動いてなさそうな」
- **答えの要点**:
  - Bot のコメントは新しく増えず、**最初のコメントが上書きで更新される**。表示の時刻は最初に書かれた時刻のまま。
  - 中身(Latest commit の番号、ready / processing)を見ると、最新の状態が分かる。

### Q15. 「Invalid supabaseUrl」/「SUPABASE_URL の形が違います」
- **ひろみの言葉**:「あ、SupabaseがURLの形になってないわ」「更新してみたけど、まだ反映されないのかなぁ」
- **答えの要点**:
  - アプリ本体は動いていて、Supabase につなぐところで止まっていた(前進のしるし)。
  - Netlify の環境変数を直しても、**すでにできている版には反映されない**。組み立て直し(Retry deploy)が要る。
  - 環境変数は、場面(本番/Deploy Preview など)ごとに別の値を持てる。確認版で使うなら Deploy Previews にも値が要る。
  - アプリの側でも、前後の空白・引用符を取り除き、形が違うときは日本語で伝えるようにした。

### Q16. 「Publish deploy」を押せばよいか
- **ひろみの質問**:「Publish deployのボタンを押せばOK?」
- **答えの要点**:
  - 押さない。これは「この版を本番として公開する」ボタン。
  - 組み立て直しは「Retry deploy」。

### Q17. ログインのユーザーはどこで作るか
- **ひろみの質問**:「ごめん、これやり方どこだっけ」
- **答えの要点**:
  - Supabase の Authentication → Users →「Add user」→「Create new user」。「Auto Confirm User」にチェック。
  - 新規登録は Authentication → Sign In / Providers の「Allow new users to sign up」をオフにする。

## 2026-11-06〜07 IFRA の取り込み(R7・R8)

### Q18. IFRA の Excel を取ってくるのに、外部の住所への接続を許可していいのか
- **ひろみの質問**:「これの接続って、やっていいものなの?」「エクセルをDLしてどこかにDBとしてアップするとか、手動作業を挟んだほうがいいとかない?」「ちなみに一般的にはAにすることってあるの?」
- **答えの要点**:
  - 住所は IFRA の公式ページのダウンロードの先。ひろみがブラウザで落としても同じファイル。安全面の差はほとんどない。
  - 手動を挟む価値があるのは「ダウンロード」より「確認」(最新の公式版か/取り込んだ数字が合っているか)。
  - 一般的には、プログラムが公式の住所から直接取る形(A)もよくある(やり直しがきく、取り違えがない)。会社では、外部とつなぐ許可はセキュリティ担当と決めることが多い。
- **結果**:ひろみがダウンロードして渡した(B)。「Aでもいい気もするけど、なんとなく」。

### Q19. SQL のファイルは全部まとめて貼るのか、1つずつか
- **ひろみの質問**:「abc全部まとめて貼ってRUN?それとも、aでRUN,bでRUN,、、?」
- **答えの要点**:
  - 1つずつ。b・c は a で作った表にデータを入れるので、順番が大事。どこで失敗したかも分かりやすい。
  - 「Success. No rows returned」は「成功。結果として返す行はない」という意味。表を作る・データを入れる SQL は、結果の表を返さないのでこう出る。

### Q20. 確認の SQL で、結果が1つしか出なかった
- **ひろみの言葉**:「3はこれで期待どおりなのか・・・?」
- **答えの要点**:
  - Supabase の SQL Editor は、複数の SQL を一度に実行すると、**最後の1つの結果しか表示しない**。出ていたのは ⑤(例外表)の結果で、これは期待どおり(8件)。
  - ①〜④を見るには、1つずつ実行する(その部分だけを選んで Run)。

### Q21. 今回の SQL は何をしたのか(ひろみの依頼で復習対象)
- **ひろみの言葉**:「これ、なにやってるかあんまりわかってないから復習対象にしておきたい!」
- **答えの要点**:
  - **a(migrations)= 表の設計図を作った**。空の表を6つと、見やすくするためのビューを1つ。
    | 表 | 中身 | 1行は何か |
    |---|---|---|
    | ifra_amendments | 改正の版(第51次)と出典 | 1つの改正 |
    | ifra_standards | IFRA の基準(263件) | 1つの基準(例:オークモス) |
    | ifra_standard_cas | 基準と CAS 番号の対応 | 基準 × CAS 番号 |
    | ifra_limits | 製品カテゴリごとの上限(4,734件) | 基準 × カテゴリ(例:オークモス × 11B = 0.1%) |
    | ifra_annex | 精油ごとの規制成分の含有率(1,031行) | 精油 × 成分(例:ティーツリー × メチルオイゲノール = 0.05%) |
    | ifra_review_items | 人が確認する項目=例外表(8件) | 確認する項目1つ |
    | ifra_annex_11b(ビュー) | Annex と 11B の上限を、つないで見せる | 精油 × 成分 × 11B の上限 |
  - あわせて、各表に「ログインした人だけが読める」決まり(RLS)を付けた。
  - **b・c(seed)= 表にデータを入れた**。IFRA の Excel をプログラムで整えて作った SQL。「0,10」→ 0.1 などに直し、元の値も残した。
  - **確認の SQL = 入ったデータを読んで、期待どおりか見た**(件数、気になる原料の上限、事前検証で使った成分、例外表)。
  - この表を使って、あとで「処方 × 精油 × Annex × 11B の上限」をつなぎ、上限に対して何倍かを計算する(R10)。

### Q22. PR を見張るのは普通か
- **ひろみの質問**:「これは見張るのが普通?」
- **答えの要点**:
  - 人のチームでも、PR を出した人が「自動チェックが通ったか」「コメントが来ていないか」を気にかけるのは普通。それを Claude に任せている形。
  - 今回の PR は SQL と文書だけで、Netlify の組み立てに影響しにくいので、見張る価値は前回より小さめ。それでも、コメントや失敗に気づける。

## 用語集

| 用語 | ひとことで言うと |
|---|---|
| Region(リージョン) | データベースなどを置く場所(国・地域)。近いほど速い |
| リポジトリ | プロジェクトのファイルと変更の歴史を入れておく場所(GitHub) |
| ブランチ | 本番(`main`)に影響しないように、別の線で作業するための枝分かれ |
| PR(プルリクエスト) | ブランチの変更を `main` に取り込んでよいか、確かめるための申請 |
| マージ | PR の変更を `main` に取り込むこと |
| ビルド(組み立て) | 書いたコードを、公開できる形にまとめる作業 |
| デプロイ | 組み立てたアプリをネット上に置いて、使える状態にすること |
| Deploy Preview | PR ごとに Netlify が作る「確認用の版」。`main` に取り込む前に確かめられる |
| 環境変数 | キーや住所など、コードに書かずに外から渡す設定の値 |
| publishable key | 公開されても大丈夫なように作られた Supabase のキー |
| Secret key / API キー | 知られると困る本物の秘密のキー |
| RLS(行レベルセキュリティ) | データベースの表ごとに「誰が読める・書けるか」を決める仕組み |
| Node.js | アプリを動かす土台のソフト。版をそろえないと動きが変わることがある |
| 404(Page not found) | 「その住所にページがない」という意味のエラー |
| プラグイン | サービスに機能を足す部品。今回は Netlify で Next.js を動かすために使った |
| Draft(下書き)PR | まだ取り込む準備ができていない PR。マージのボタンが押せない |
| Retry deploy | 同じ中身で組み立て直すこと。環境変数を変えたあとに使う |
| Publish deploy | 選んだ版を本番として公開すること |
| SQL Editor | Supabase の画面で SQL を書いて実行する場所 |
| テーブル(表) | データベースの中の表。列(項目)と行(1件ずつのデータ)でできている |
| ビュー | いくつかの表をつないだ「見え方」を保存したもの。データは持たない |
| migration(マイグレーション) | 表の設計図を作る・変える SQL。番号順に1回だけ実行する |
| seed(シード) | 表に最初に入れておくデータ |
| CAS 番号 | 化学物質ごとに付いている番号。名前の揺れがなく、表どうしをつなぐのに使う |
| Success. No rows returned | 成功。結果として返す行はない(表を作る・データを入れる SQL ではこう出る) |
