- 新しいものを下に足す。学びのログ(`learning-log.md`)は節目のふり返り、このファイルは日々の疑問の記録。

## 2026-11-06 実装フェーズの準備(土台 R18)

### Q1. Supabase の Region
- **ひろみの質問**:「regionはap-southeast-1なのかな?」
- **答えの要点**:
  - `ap-southeast-1` はシンガポール。東京は `ap-northeast-1`。
  - Region は作ったあとに変えられない。中身が空のうちなら、消して作り直すのが一番楽。
  - 遠いと画面の反応が少し遅くなる(シンガポールだと東京より 0.07秒ほど)。利用者が1人なら実害は小さい。
- **結果**:東京で作り直した。

### Q2. 「Asia-Pacific」を選べばよいか
- **ひろみの質問**:「region、asia-pacificでいい?」
- **答えの要点**:
  - 「Asia-Pacific」のような大きな地域を選ぶと、その中のどこに置くかは Supabase が決める(最初にシンガポールになったのはたぶんこれ)。
  - 個別の地域を選べる表示に切り替えて「Tokyo」を選ぶ。

### Q3. さくらサーバを使えないか
- **ひろみの質問**:「わたしさくらサーバを持ってるんだけどそこは変?」
- **答えの要点**:
  - 変ではない(持っているものを使えば費用が増えない)。
  - ただ、Next.js のアプリは「サーバの上で常に動いているプログラム」が要る。共用のレンタルサーバでは、それを置き続けられないことが多い。
  - VPS なら動かせるが、サーバの手入れ(更新・セキュリティ)を自分で続ける必要がある。
- **結果**:Netlify(無料プラン)に置く。

### Q4. ドメインはどうするか
- **ひろみの言葉**:「ドメインは持ってる!まぁあとあと移管するとかでいいか。」
- **答えの要点**:
  - 【推測】ドメインの「移管」(管理する会社を変えること)は要らない。持っているドメインの設定で、`tool.polearoma.com` のような住所を Netlify に向けるだけでよい。
  - 後でやる。

### Q5. 「PR を見張る」とは
- **ひろみの質問**:「これどういうこと?具体的におしえてほしいな」
- **答えの要点**:
  - PR で何か起きたら(Netlify の組み立ての失敗、コメントなど)、GitHub から Claude に知らせが届き、Claude が見て対応する。
  - 見張っていないと、ひろみが気づいて伝えるまで、失敗がそのままになる。
  - Claude が PR を `main` に取り込む(マージ)ことはしない。Netlify の管理画面やスマホでの結果は、Claude からは見えない。

### Q6. Netlify の設定画面が見つからない
- **ひろみの言葉**:「Project configurationがみつからないなー」→「あ、githubの該当リポジトリとの接続ができてなかったみたい」
- **答えの要点**:
  - サービスの画面の名前はよく変わる(Claude の案内が古いこともある)。見つからないときは、並んでいる項目の名前を伝えると早い。
  - 実際の原因は、Netlify とリポジトリがまだつながっていなかったこと。

### Q7. Netlify の Build settings に何を書くか
- **ひろみの質問**:「Build settingsって何を書けばいいの?」
- **答えの要点**:
  - Branch to deploy:`main`(本番として公開するブランチ)
  - Base directory:`web`(アプリ本体のフォルダ)
  - Build command:`npm run build`(アプリを組み立てる命令)
  - Publish directory:`web/.next`(組み立てた結果の置き場所。自動で入ればそのまま)
  - 実際は、リポジトリの `netlify.toml` に書いた設定が優先される。

### Q8. Supabase の URL と publishable key は「秘密の値」か
- **ひろみの質問**:「ちなみにこれって「秘密の値」に該当する??」
- **答えの要点**:
  - どちらも厳密には秘密ではない。URL は「住所」。publishable key は、ブラウザに渡しても大丈夫なように作られたキー。
  - 安全なのは、データベースの表ごとに「誰が読める・書けるか」の決まり(RLS)を付けている場合だけ。処方の表を作るときは必ず付ける。
  - 本当に秘密なのは、Claude API のキーと Supabase の Secret key(知られると、お金を使われる/データベースに何でもできる)。
  - それでもチャットやリポジトリには書かない(毎回「書いていいキーか」と迷わないため)。

### Q9. Netlify が「秘密の値にしろ」と何度も勧めてくる
- **ひろみの質問**:「って注釈出てるけど大丈夫なのかな」「ってもう一回言われたよ〜〜」「これってsupabaseのpole-aroma-work-managementのproject URLなんだよね?」
- **答えの要点**:
  - 【推測】Netlify は値の中身ではなく、名前(URL・KEY など)だけを見て一律に注意を出している。
  - そう、Supabase のプロジェクトの Project URL(`https://〜.supabase.co`)。
  - チェックしてもしなくても、安全面の差はほとんどない。チェックすると、値があとで見られなくなるだけ。

### Q10. 本番の組み立てが失敗した
- **ひろみの言葉**:「Deploy failed for pole-aroma-work-management って出たなぁ」
- **答えの要点**:
  - 想定どおり。`main` にまだアプリ本体(`web/`)がないため。PR を取り込めば通るはず。
  - PR 用の確認版(Deploy Preview)は成功した。

### Q11. 確認はスマホでないとだめか
- **ひろみの質問**:「これはスマホで見ないとだめ?PCは微妙?」
- **答えの要点**:
  - ログインの確認なら PC で十分。
  - スマホで確かめる意味が大きくなるのは、写真を上げる画面(R1)を作ってから(HEIC、カメラからの撮影)。

## 用語集

| 用語 | ひとことで言うと |
|---|---|
| Region(リージョン) | データベースなどを置く場所(国・地域)。近いほど速い |
| リポジトリ | プロジェクトのファイルと変更の歴史を入れておく場所(GitHub) |
| ブランチ | 本番(`main`)に影響しないように、別の線で作業するための枝分かれ |
| PR(プルリクエスト) | ブランチの変更を `main` に取り込んでよいか、確かめるための申請 |
| マージ | PR の変更を `main` に取り込むこと |
| ビルド(組み立て) | 書いたコードを、公開できる形にまとめる作業 |
| デプロイ | 組み立てたアプリをネット上に置いて、使える状態にすること |
| Deploy Preview | PR ごとに Netlify が作る「確認用の版」。`main` に取り込む前に確かめられる |
| 環境変数 | キーや住所など、コードに書かずに外から渡す設定の値 |
| publishable key | 公開されても大丈夫なように作られた Supabase のキー |
| Secret key / API キー | 知られると困る本物の秘密のキー |
| RLS(行レベルセキュリティ) | データベースの表ごとに「誰が読める・書けるか」を決める仕組み |
| Node.js | アプリを動かす土台のソフト。版をそろえないと動きが変わることがある |
