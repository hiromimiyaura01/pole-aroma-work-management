# 現状調査メモ:手書きの処方ノート

- 確認日:2026-11-05
- 対象:ひろみの処方ノートの写真2枚(Google ドライブ経由。iPhone で撮影)
  - 1枚目:「Tea 012」と「Tea 013」が見開きで並んだページ(PNG)
  - 2枚目:「Tea 004」のページ(JPEG)
- 目的:手書きノートを AI で読み取って処方の下書きを作れるか、作る前に確かめる
- 注意:**処方の配合(滴数など)はここに転記しない**(企業秘密にあたるため)。書き方の特徴と、読み取りの課題だけを記録する。

---

## 1. 画像の形式について【事実】

- 最初にアップされた HEIC 形式(iPhone の標準)は、今の Google ドライブ連携では中身を読めなかった。
- JPEG・PNG に変換したものは読めた。解像度は 480×640 程度(縮小版)だったが、読み取りには十分だった。
- → 【推測】プロダクトでは **HEIC を受け付けて変換する処理** が必要。

## 2. 読み取りの結果【事実】

### 汎用の文字認識(Google ドライブの OCR)
- 1枚目は文字として取り出せたが、**誤りが多く、構造も崩れた**。
  - 例:「Bergamot」→「Веда шот」(キリル文字になった)、「Petitgrain」→「Petigmin」、「Hinoki」→「Hi noki」
  - 左右2列(Tea 012/013)が混ざり、どの数字がどの精油のものか分からなくなった。
- 2枚目は何も取り出せなかった。

### 画像を理解できる AI(Claude)が画像を直接見た場合
- 2枚とも、**精油名・数字・グループ分け・バージョン名を問題なく読めた**。
- 【推測】汎用の OCR ではなく、**画像を理解できる AI に「香りの処方ノートである」という前提を与えて読ませる** と、実用的な精度が出る見込みがある。ただし確認したのは2枚だけで、ひろみの字がきれいなことにも助けられている。

## 3. ノートの書き方の特徴【事実】

| 特徴 | 内容 | 設計への影響【推測】 |
|---|---|---|
| シリーズ名+番号 | 「Tea 004」「Tea 012」「Tea 013」のように、同じシリーズで試作を重ねている | 処方を「シリーズ(処方ファミリー)」と「バージョン」に分けて記録する。試作の履歴をたどれるようにする |
| バージョンを並べて比較 | 見開きで 012 と 013 を並べ、精油の入れ替えや量の調整をしている | バージョン間の差分(何を足した・減らした)を表示できると便利 |
| ノートごとのグループ | 中かっこでトップ/ミドル/ベースらしきグループに分け、横に小計を書いている | グループと小計も読み取る。**小計と合計が合っているかを計算で確かめれば**、読み取りミスに気づける |
| 略称 | 「O.S」(オレンジスイートと思われる)、「Eremi」(エレミと思われる)、「Cederwood. V」(シダーウッド・バージニアと思われる)など | 略称を、価格表や基準データの精油名に **対応づける(名寄せ)** 仕組みが必要。ひろみ専用の略称辞書を育てる |
| 書き直し | 一度書いた数字を線で消して書き直している箇所がある | 最終的な値が曖昧な箇所は、AI が「確認してください」と印をつけ、人が決める |
| グループの外の記載 | かっこの外に書かれた精油がある | 処方に含むのか、候補のメモなのかを人に確認する |
| 単位の記載がない | 数字だけで、滴・ml・比率のどれかは書かれていない。合計が 20 のページと 200 のページがある | 「比率」として記録し、作る量に合わせて滴数に換算する設計が自然(要確認) |
| 精油以外と思われる素材 | 「Tea」「Amber」など、単一の精油ではなさそうな名前がある | 香料(フレグランスオイル)やアコードの場合、成分が分からないので IFRA の確認ができない。「成分不明」として扱う(要確認) |
| 危険原料の候補 | オークモスを含む試作がある | ピローミスト(IFRA カテゴリ 11B)なら、オークモスは 0.1% の上限に当たる。**実データで「赤」が出る具体例** になる |

## 4. ここから言えそうなこと【推測】

1. **手書きノートの読み取りは、MVP の中心機能として実現できそう**。汎用 OCR との差がはっきり出たので、「なぜ AI(Claude API)を使うのか」をポートフォリオで説明しやすい。
2. AI に任せるのは「読み取って下書きを作る」ところまで。名寄せの候補、曖昧な箇所の印、小計チェックの結果を見せて、**人が確認してから保存する**。
3. 処方はバージョン管理が前提になる。データ設計(SQL)では「シリーズ → バージョン → 配合行」の構造にする。
